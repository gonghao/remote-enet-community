# 中心协议（规范框架）

记录日期：2026-11-19。本文定义“中心协调”模式下各方的职责、信任关系和必须满足的约束，用作后续 API 与票据契约的基线。**目前尚未实现**：具体 API、票据编码、续租协议和数据库结构须在实现前另立契约。本文不修改现有 `renet1:`、Settings 或 session 消息格式。

部署模式与配对入口见 [DEPLOYMENT-MODES](DEPLOYMENT-MODES.md)。官方中心是按本协议运营的一个实现，其服务端代码不在本仓库；第三方可以按本文自行实现中心。

## 1. 角色与组件

| 组件 | 职责 | 是否在逐包转发路径上 |
|---|---|---|
| 中心 | 账号与设备资格、数字码签发与核销、Hub 节点登记与分配、签发连接票据、并发租约 | 否 |
| Hub | 验证票据、执行准入与租约、配对两条连接并转发密文、上报心跳与用量 | 是，只转发密文 |
| Operator | 登录中心、选择节点、生成数字码、确认来访设备、端到端会话的一端 | 是（端点） |
| Client | 用数字码向中心兑换授权，连接指定 Hub，端到端会话的另一端 | 是（端点） |
| API 入口代理（可选） | 为难以直连中心的网络提供备用 HTTPS 入口 | 否 |

中心和 API 代理都不参与逐包转发。Hub 不持有车辆载荷的解密密钥。`carside` 不解析隧道内容、不提权、不配置 L3；本项目不增加车辆编码或刷写的业务逻辑。

## 2. 状态归属

| 状态 | 归属 | 要求 |
|---|---|---|
| 账号、授权期限、设备公钥绑定、节点登记 | 中心，持久保存 | 以服务端时间为准 |
| 数字码预留与核销、账号级并发占位 | 中心，原子操作 | 不能依赖最终一致的存储；跨 Hub 共用同一份并发约束 |
| 活动连接、配对占位、限流、票据使用记录 | Hub，内存 | Hub 不需要账号数据库，但不是完全无状态 |
| 设备身份、已信任对端 | 各端本地 | 已有本地信任只省去重复建立设备信任，不能绕过中心的授权检查 |

中心只保存必要的元数据，默认不收集 VIN、诊断载荷、HSFZ 抓包或原始邀请码。Operator 的显式抓取继续保存在本地。

一个 Operator 同时只服务一个 Client 的既有约束保持不变。

## 3. Hub 注册与准入

新增节点的流程：

1. 部署同一个 Go Hub，配置公网监听入口，生成本节点身份密钥。
2. 管理员在中心登记地址、端口、区域、节点公钥指纹和容量属性。节点须证明自己持有私钥，并通过连通性校验后才能上线。任意来源上报的地址不能自动进入可信节点池。
3. Hub 配置中心验签公钥和节点级凭据，上报心跳、版本、负载、用量和会话状态。节点凭据只能管理节点自身的状态。
4. 中心把已批准节点的地址和身份下发给客户端，并签发绑定该节点的票据。增加节点不需要在 Hub 上创建用户，也不需要重新发布 Client。

准入规则：

- Hub 入站时必须验签，并核对设备身份、角色、对端、会话、节点和期限。缺少验签配置、票据无效或身份不匹配时拒绝连接，不能回退到无鉴权模式。
- Hub 在本地验证票据，不为每个数据包请求中心。
- 短期票据不能解决长连接的撤销问题。等待配对、配对完成、续租、重连各检查点的行为，以及租约到期后的处理，须在授权契约中分别规定。
- 现有 Hub 路由头的 token 上限为 1024 字节，设计票据格式时须核对尺寸。

## 4. 接待流程

1. Operator 登录中心，中心确认账号有效、设备有资格、并发额度允许。
2. Operator 选择 Hub 节点并开始接待。界面可以展示区域、实测延迟和负载，但 Operator 到 Hub 的单段延迟不代表端到端质量。
3. 中心确认节点可用，生成 8 位数字码，绑定本次接待、Operator 身份、所选 Hub 和截止时间。
4. 客户使用通用 Client，首次选择 ENET 网卡并保存，输入数字码后点击连接，不需要手动填写中心或 Hub 地址。
5. Client 向中心兑换数字码并提交本机身份。中心预留本次配对，校验账号、数字码和并发资格。初版默认由 Operator 确认来访设备。
6. 中心给两端签发受限票据，下发 Hub 地址、Hub 指纹和期望的对端身份。双方连接同一个 Hub，由端到端认证层确认对端设备身份。
7. 配对成功后核销数字码；失败或超时则在有限时间内释放预留。短暂断线可在同一会话授权内自动重连；结束接待后再连接需要取得新的会话授权。

网卡缺失、未发现车辆、Operator 忙、授权到期、数字码无效、节点离线这几种情况，界面要分别给出明确原因。Client 始终可以主动停止连接。

## 5. 数字码、票据与信任

| 信息 | 用途与边界 |
|---|---|
| 登录凭据 | 确认账号与设备资格，不能作为 Hub 转发凭据 |
| 数字码 | 定位并发起一次接待配对；预留不等于核销 |
| 中心签名票据 | 允许指定设备以指定角色连接指定 Hub 与会话，受期限、额度和租约约束 |

- 数字码由中心保证在有效期内不冲突，并设置总量预算、有效期，以及按账号、设备和来源的尝试次数限制。
- 数字码同时作为两端之间的 PAKE 口令（见 [DEPLOYMENT-MODES 第 4 节](DEPLOYMENT-MODES.md#4-8-位数字码必须作为-pake-口令)）。这样，中心或 Hub 即使被攻破，也不能冒充对端设备。
- 票据至少绑定授权主体、设备公钥身份、角色、对端、会话、Hub、有效期和防重放标识。编码格式、密钥轮换、时钟偏差、续租与重放检查留给独立契约。
- 节点身份和对端身份分开校验：外层钉住 Hub 公钥，内层确认 Operator / Client 公钥，两种指纹不能混用。
- 数字码过期与活动会话的授权到期是两件事。数字码计时结束不能切断已经建立的诊断会话。

## 6. 授权期限、中心故障与会话结束

生成数字码、建立新会话、重连和续租都按中心策略检查，不依赖本机时钟或界面按钮。

| 事件 | 目标行为 |
|---|---|
| 授权自然到期 | 提前提示，禁止新会话；活动会话是否有宽限期、宽限多久，由中心策略决定 |
| 中心请求短暂失败 | 不因一次失败中断健康的通路，只在已有有效票据或租约及明确的宽限范围内继续 |
| 长期无法访问中心 | 不能无限续用，也不能从缓存生成新授权 |
| 管理员封禁或安全吊销 | 与自然到期分开处理，按约定的撤销传播和租约策略执行；离线验签做不到即时全局吊销，不能这样宣称 |
| 用户结束接待 | 撤销本次接待的后续接入资格，回收连接和占位；旧的设备信任不能自动抢占新的接待 |

车辆诊断进行中，不能出现未经说明的后台硬切断，也不能以“保护会话”为由无限绕过期限。

## 7. 多节点与迁移

- 两端必须被分配到同一个 Hub。Operator 可以选择节点，但中心仍要检查节点状态、账号策略和全局并发，不能只相信客户端上报的区域或地址。
- 节点选择应参考两端到候选节点的实测质量。跨区域的两端需要实测，不能按地理位置推定。
- 数字码生成后固定对应一个 Hub。切换节点需撤销未使用的旧码并重新生成；活动诊断不自动跨节点迁移。
- 节点故障会断开已有 TCP 连接。新的授权会话可以重新选择节点，不承诺无损迁移，也不重放旧的车辆请求。
- 节点替换、失联后释放占位、跨区迁移都必须通过有期限的租约处理，防止旧节点恢复后与替代节点同时占用额度。

## 8. API 入口与回退

中心可以有多个可信 HTTPS 入口，例如默认入口加一个面向特定网络的代理入口。

- 备用入口及其信任策略须随安装包预置，或来自此前已验证的配置。远程更新入口列表必须验证来源；不能在中心不可达时，再向同一个中心查询备用地址。
- 网络超时、TLS 错误和可重试的服务错误可以触发有限次数的回退。账号停用、授权到期、数字码错误等明确的业务拒绝，不能通过换入口重试来绕过。所有入口共用限流、数字码核销和并发额度。
- 登录、兑换、占位、续租等写操作须带幂等请求标识，并提供结果查询。请求超时不等于中心没有执行，切换入口后不能重复消费数字码或创建两个会话。
- 普通 HTTPS 反向代理会终止客户端 TLS，能看到 API 凭据和数字码，属于受信基础设施。代理不得记录密码、登录令牌、数字码和完整票据，不持有中心签名私钥，也不能自行签发授权。
- 登录、权限查询、数字码兑换和授权结果禁止使用公共或共享缓存。
- 代理只改善客户端到入口这一段的可达性，不能替代中心本身的容灾。

## 9. 密钥边界

| 位置 | 可以持有 | 不应持有 |
|---|---|---|
| 中心 | 账号与授权事实、中心授权签名私钥、节点登记与策略 | 车辆载荷、端到端会话密钥 |
| Hub | 本节点身份私钥、节点级凭据、中心验签公钥、受限运行状态 | 中心签名私钥、账号密码库、两端身份私钥 |
| API 代理 | 自身 TLS 与回源配置、最小必要凭据 | 中心签名私钥、第二套授权数据库 |
| Client / Operator | 本机身份、中心信任配置、当前有效的受限凭据 | 中心签名私钥、其他设备的身份私钥 |

- 中心授权签名密钥与安装包更新签名密钥分开管理。
- 单个 Hub 节点的凭据不能签发全平台授权。节点计量与中心租约须对账。
- 恶意或故障的 Hub 可以阻断、拖慢连接或伪报用量，所以 Hub 仍是受信的执行节点，但它读不到车辆载荷。

## 10. 威胁模型

| 场景 | 防御目标 |
|---|---|
| 修改本机的到期判断，继续使用某个中心及其 Hub | 由该中心和 Hub 在服务端检查资格、票据和租约；修改本机界面或时间不能获得额外权限 |
| 修改程序，但持有合法账号、设备密钥和票据 | 只能在服务端允许的额度内使用。设备密钥不能证明程序未被修改 |
| 复制、伪造或跨设备重放票据 | 中心私钥不分发；Hub 校验签名、设备私钥持有、角色、对端、节点、会话、期限，并配合重放检查和全局并发控制 |
| 用户改用自己的中心和 Hub | 这是本项目支持的合法自建用法（见 [DEPLOYMENT-MODES](DEPLOYMENT-MODES.md)），不属于需要防御的攻击 |

- 端到端 TLS 和公钥钉住保护的是链路和对端身份，不是防复制机制。
- 客户端上报的版本号、文件哈希或“完整性检查通过”标志，都不能证明程序未被修改。
- 发布签名（macOS Developer ID 与公证、Windows Authenticode、签名更新清单）帮助用户识别官方发行物、发现被替换的安装包，但不是服务端的远程程序证明。

## 11. 一致性测试要求

离线自动化测试只使用 loopback、`net.Pipe` 和内存传输，至少覆盖：

- 数字码并发兑换、PAKE 猜错与次数用尽；
- 跨 Hub 的额度控制；设备、角色、对端、节点不匹配；
- 票据过期与重放、旧租约隔离；
- 中心断连、入口回退、写请求幂等；
- 正常结束与资源回收。

原有的转发、端到端加密和取消行为不能退化。实际公网环境的验收单独执行、单独记录，不放进普通离线 CI。

协议定稿后，计划同时发布票据与 PAKE 的测试向量，供第三方中心实现验证兼容性。

## 12. 待定参数

中心 API 形态与版本协商、登录方式、PAKE 选型、8 位码有效期与尝试预算、Operator 确认策略、设备数与并发额度、票据与租约期限、撤销传播方式、自然到期宽限期、入口回退预算、计量口径。默认值在契约中明确，不在实现中临时推定。
