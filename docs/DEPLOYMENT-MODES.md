# 部署模式与配对入口

记录日期：2026-11-19，2026-11-20 随 R3、R5 更新。本文是设计基线，除第 8 节列为“已实现”的部分外，均为规划，不代表程序已经支持。中心相关的协议框架见 [CENTER-PROTOCOL](CENTER-PROTOCOL.md)，整体架构见 [DESIGN](DESIGN.md)。本文不修改现有 `renet1:` 邀请码、Settings 或 session 消息格式。

## 1. 原则

**一套代码，模式由运行配置和用户输入决定，不靠构建区分。**

- Client 只有一个通用版本。直连、自建 Hub、官方中心三种用法使用同一个 Client 二进制。
- Operator 同样只有一个版本。自用部署与社区自建的区别只在 Operator 的运行配置（公网入口、端口、身份目录），不需要特殊构建。
- 官方发行版与社区构建使用同一份功能代码，差异只在发行层面（第 6 节），不存在只有官方版才有的功能分支。

## 2. 三种模式

| 模式 | 适用场景 | 数据路径 | 需要的服务 |
|---|---|---|---|
| 直连 | Operator 有公网地址或 DDNS，可做端口转发 | Client → Operator 内嵌 Hub | 无 |
| 自建 Hub（已实现，台架验收待执行） | 两端都在 NAT 后，或不想暴露 Operator 地址 | 两端分别出站连接自建 Hub | 自行运行独立 Hub 程序 `renet-hub`，并在其配置中列出 Operator 的签发公钥，见 [SELFHOST](SELFHOST.md) |
| 中心协调（Go 端已实现，中心服务端另行实现；与真实中心的联调和人工验收待执行） | 需要账号、免配置数字配对、多节点调度 | 两端连接中心分配的 Hub | 官方中心，或按 [CENTER-CONTRACT](CENTER-CONTRACT.md) 自建的中心；Hub 以 `renet-hub` 的中心模式运行，见 [CENTER-CLIENT](CENTER-CLIENT.md) |

三种模式下，车辆数据都在两端之间端到端加密，Hub 只转发密文，`carside` 的黑盒边界不变。

## 3. 配对入口

Client 使用同一个输入框，按输入格式自动识别：

| 输入 | 适用模式 | 说明 |
|---|---|---|
| 原始 `renet1:` 邀请码 | 直连（已实现）；自建 Hub（已实现，版本 2 邀请码额外携带短期不记名票据，`renetd invite --hub` 或 GUI 生成） | 自带地址、Operator 指纹、首次配对令牌和有效期 |
| `地址:端口` + 8 位数字码 | 直连；自建 Hub | 直连已实现（[PAIRING](PAIRING.md)），待假车与公网验收。自建 Hub 下输入同样的「Hub 地址 + 8 位码」：Hub 配置了 `pairing_operator` 的那台 Operator 在发码期间开放配对入口（能力 `pair-hub/1`，Hub 指纹写入 PAKE），已实现，台架验收待执行（[SELFHOST §7.2](SELFHOST.md#72-hub-地址--8-位码)）。便于口述或在聊天工具中发送；地址可以是 DDNS 域名 |
| 8 位数字码 | 中心协调 | 已实现（R5，[CENTER-CLIENT](CENTER-CLIENT.md)），待与真实中心联调。需要 Client 已配置中心（官方构建有默认值）；未配置中心时提示“未配置中心”，不发请求。兑换后经中心分配的 Hub 完成 PAKE 与双端 SAS 核对，Operator 须输入客户读出的 6 位校验码 |

配对成功后，双方保存对端身份，之后重连不需要任何码。数字码只用于首次配对，不是长期凭据。

已否决的分享方式（2026-11-18）：邀请二维码图片和邀请文件在聊天工具里传播不便；第三方短链接服务需要保存映射，并会看到首次配对令牌。最终只保留原始邀请码和数字码两种入口。

Peer ID 是设备公钥指纹，用于核对“连接的是不是原来那台设备”。它不含连接地址，也不是授权凭据，可以公开显示。界面默认显示设备名加短 ID，完整 ID 放在详情里并可复制（2026-11-19 确认）；短 ID 只用于显示，比较身份时一律使用完整指纹。

## 4. 8 位数字码必须作为 PAKE 口令

通用 Client 没有预置 Operator 指纹。如果直接把 8 位码当令牌发给“地址指向的服务器”，攻击者只要劫持 DNS 或处于路径中间，就能截获数字码、转发连接并冒充 Operator。因此：

- 8 位码作为 PAKE（口令认证密钥交换，已选 CPace，见 [PAKE 选型](research/pake-selection.md)）的口令使用，不在网络上以任何可离线验证的形式出现。
- PAKE 的密钥确认必须覆盖双方设备公钥指纹。配对成功即证明对端知道同一个码。直连模式把对端公钥写入本地长期信任，之后按现有方式钉住指纹；中心模式只在本次接待内钉住对端，见 [CENTER-CONTRACT 第 10 节](CENTER-CONTRACT.md#10-中心模式的首次配对)。
- 攻击者每次在线尝试只能猜一次，猜中概率为 10⁻⁸。直连模式下，Operator 端还要限制有效期、单码失败次数和总尝试预算，配对成功或超出预算后立即作废该码；中心模式的码在兑换时即核销，预算见契约。
- 数字码由密码学随机数生成，按字符串处理，保留前导零，可分组显示（如 `4827 1936`）。
- 直连模式下，数字码只保存在 Operator 内存中，重启后失效。
- 中心协调模式同样使用 PAKE，这样 Hub 或网络路径即使被攻破，也不能冒充对端设备。中心分配数字码，所以中心和 API 入口在首次配对时是受信方：它们被攻破时可以冒充对端，两端口头核对由 PAKE 会话密钥派生的短校验码（SAS）可以发现。

PAKE 选定自行实现 CPace（draft-irtf-cfrg-cpace-21，ristretto255 套件），引入依赖时在 commit 中写明理由。直连与中心模式使用同一套消息与状态机（[CENTER-CONTRACT 第 10.2 节](CENTER-CONTRACT.md#102-sas-与承诺)），直连模式默认不显示 SAS，细节在 R2 规定。现有 128 位配对令牌不能简单截短为 8 位直接使用。

## 5. 地址不是秘密

Operator 的公网地址无法对客户保密：原始邀请码包含地址，连接建立后对端用 `netstat` 就能看到，把地址编译进程序也能用 `strings` 提取。所以：

- 直连模式的安全依靠 TLS 设备身份、PAKE 和尝试限制，不依靠地址保密。
- 自用部署把地址写进私有配置，只是运维习惯，不是安全措施。
- 如果不希望客户知道 Operator 所在网络的地址，应改用自建 Hub 或中心协调模式，由中继承载流量。

## 6. 中心地址可配置

- Client 和 Operator 的中心地址都是运行配置，代码中不写死任何中心。官方发行版只是把默认值指向官方中心。
- 不同中心是不同的信任根。在一个中心下建立的信任与授权，不能自动带到另一个中心使用。
- 界面应显示当前使用的中心，切换中心需要用户明确操作。

官方发行版与社区构建的区别：

| 项目 | 官方发行版 | 社区构建 |
|---|---|---|
| 功能代码 | 本仓库公开代码 | 相同 |
| 默认中心地址 | 官方中心 | 无（直连与自建 Hub 不需要中心） |
| 代码签名、公证 | 有 | 自行决定 |
| 自动更新通道 | 官方签名的更新源 | 自行决定 |
| 服务资格 | 由官方中心与官方 Hub 在服务端执行 | 不适用 |

## 7. 代码边界

- 本仓库包含 Client、Operator、Hub、加密与会话协议、Hub 的票据验签，以及 Client / Operator / Hub 与中心交互的协议实现。
- 官方中心的服务端实现不在本仓库。中心协议以 [CENTER-PROTOCOL](CENTER-PROTOCOL.md) 为公开规范，计划同时提供一致性测试向量，第三方可以据此自行实现中心。
- 暂不提供参考中心实现。自建需求优先由直连和自建 Hub 两种模式覆盖。
