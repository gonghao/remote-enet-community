### alive 的新观察与限制

## 补充：显卡直通 VM 脱离 RDP 的桌面验证

同日按用户要求验证无需 Mac 持续连接 RDP 的操作方式。Windows 识别到直通的 Intel UHD 770，以及 RDP 的 Microsoft Remote Display Adapter。本轮没有安装显示驱动、修改显卡直通配置、配置自动登录或更改锁屏策略。

先在原 RDP 会话中启动一个自建 WinForms 测试窗口，用真实鼠标点击按钮，确认计数从 0 变为 1。核对当前用户名与会话 ID 后，用 `tscon 2 /dest:console /v` 将该用户会话切到控制台；这里的 `2` 只是本次实际会话 ID，后续必须重新查询。该切换方式也用于微软的 [UI 测试配置说明](https://learn.microsoft.com/en-us/azure/devops/pipelines/test/ui-testing-considerations?view=azure-devops)。

| 进程是否处于 RDP 桌面 | `SM_REMOTESESSION=true` | `SM_REMOTESESSION=false` |

另在控制台会话中调用 `EnumDisplaySettings`，只枚举出 640×480、32 bpp 的模式。用 `ChangeDisplaySettingsEx(..., CDS_TEST, ...)` 对 1920×1080、1280×720、1024×768 做支持性检查，全部返回 `-2 / DISP_CHANGE_BADMODE`；`CDS_TEST` 只验证支持性，不实际切换模式，见[微软 API 说明](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-changedisplaysettingsexw)。因此当前环境不能仅靠正常分辨率设置获得上述模式。

该阶段结论：VM 已有可截图、可输入的无 RDP 控制台回退路径，但验证的是 Basic Display 输出，不是直通 UHD 770 的显示输出或 GPU 加速。640×480 不足以作为 E-Sys / ISTA 的后续标准测试桌面，随后按用户要求继续验证虚拟显示驱动，见下节。该阶段结束时移除自建测试窗口及其临时计划任务，保留 SSH 与现有按需桌面代理；用户会话仍在控制台，可以正常重新通过 RDP 登录。

Wave 4 的 Windows 原生测试实跑通过：TCP 反向四元组解析到独立子进程 PID 与创建时间；两个本地端口共享 owner；两个竞争子进程得到明确 `ErrBusy`，上游没有开流；最后连接释放后，新子进程接管并 echo，随后端口与 owner 归零。纯 helper 入口的顶层 skip 不代表跳过了这些核心检查。

最终代码另部署为真实 Windows Operator / Linux Client。双方启用 `--connection-test --connection-test-timeout 3s --status-interval 1s`，每侧均完成 10 个 probe、每方向 1,048,576 字节的专用测试，新的会话车辆转发字节保持为零。随后在 Windows 用 PowerShell 发送一次只读 VIN 请求，收到 ACK 与模拟 VIN；Operator 记录 In=39、Out=11 字节，与本次透明 HSFZ 帧长度相符，连接结束后 owner/活动连接归零。Windows 某些探测测得 RTT=0，仍有有效样本，程序正确显示 `rtt_valid=true`。

新测试二进制路径首次运行时，Windows 自动生成了只针对 `renetd-wave4.exe` 的入站阻止规则，优先于既有端口允许规则，导致远端拨号超时而本机可连。核对程序路径后，仅禁用这两条本次测试应用的阻止规则，连接即恢复；没有关闭系统防火墙或放宽原有测试允许规则的来源范围。这属于分发/防火墙预检需处理的环境事实，不是每条 TCP 连接都需要新增规则。
